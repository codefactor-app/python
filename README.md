# Codefactor для Python

Codefactor — локальный статический анализатор, который помогает находить сложный код, дублирование и проблемы в зависимостях до рефакторинга и ревью. Этот пакет устанавливает консольную команду через pip для работы в вашем проекте.

Анализатор поддерживает PHP, Python, Rust, JavaScript и TypeScript: выбор пакета определяет способ установки, а не список доступных языков. Исходный код анализируется локально, не исполняется и не отправляется во внешний сервис.

## Что даёт анализ

| Задача | Что вы получаете |
| --- | --- |
| Найти места для рефакторинга | Размер функций и файлов, число параметров, вложенность, цикломатическая и когнитивная сложность, замечания с файлами и строками |
| Разобраться в незнакомом проекте | Графы вызовов, зависимости между каталогами и модулями, переходы к исходникам в локальном веб-интерфейсе |
| Проверить структуру проекта | Поиск дублирования, циклов зависимостей и нарушений заданных границ архитектурных слоёв |
| Оценить потенциально дорогой код | Статические оценки роста числа операций при увеличении размера входных данных |
| Контролировать изменения | Настраиваемые пороги, отчёты для ревью и CI, baseline для работы с существующими замечаниями |

После `scan` вы видите сводку проекта, метрики и замечания с уровнем, расположением и нарушенным порогом. Это помогает выбрать участок для проверки и сравнивать изменения по одним критериям.

## Установка

Установка напрямую из GitHub не требует регистрации пакета в PyPI. **Пока публичный репозиторий порта пуст, эти команды недоступны:** готовый самостоятельный CLI уже можно скачать из [релизов Codefactor](https://github.com/codefactor-app/core/releases). Инструкции ниже рассчитаны на опубликованный пакет в этом репозитории.

Нужны Python >=3.10, pip и Git. Рекомендуется отдельное виртуальное окружение проекта:

```sh
python -m venv .venv
. .venv/bin/activate
python -m pip install "codefactor @ git+https://github.com/codefactor-app/python.git@main"
codefactor --version
```

В PowerShell активируйте окружение командой `.venv\Scripts\Activate.ps1`. Команды анализа ниже выполняются с активным окружением; без активации используйте `./.venv/bin/codefactor` на Linux/macOS или `.venv\Scripts\codefactor.exe` на Windows.

Сохраните зависимость в отдельный `requirements-codefactor.txt` для установки на других машинах:

```text
codefactor @ git+https://github.com/codefactor-app/python.git@main
```

При установке выбирается последний стабильный бинарь анализатора из [GitHub Releases](https://github.com/codefactor-app/core/releases), проверяются размер и SHA-256. Поддерживаются Linux, macOS и Windows на x64 и ARM64. Для скачивания нужен доступ к GitHub; токен не требуется. После установки команды работают без сети.

## Быстрый старт

Из корня проекта выполните:

```sh
codefactor scan .
```

Для первого запуска конфигурация не нужна. Лучше анализировать корень проекта, чтобы учитывать метаданные импортов и зависимостей, а область анализа ограничивать через YAML.

Чтобы увидеть все замечания и сохранить отчёт:

```sh
codefactor scan . --all
codefactor scan . --format json --out codefactor-report.json
```

Консоль по умолчанию показывает до 50 замечаний. `--all` снимает это ограничение; экспортируемый JSON всегда содержит полный отчёт. Коды завершения помогают отличить найденные нарушения от сбоя команды — таблица приведена в разделе CI.

## Конфигурация проекта

Создайте `analyzer.yaml` в корне проекта. Например, для Python:

```yaml
config_version: 1
languages:
  enabled: [python]
paths:
  include: ["**"]
  exclude:
    - "**/test/**"
    - "**/tests/**"
    - "**/test_*.py"
    - "**/*_test.py"
    - "**/conftest.py"
    - "**/fixtures/**"
    - "**/generated/**"
    - "**/*_pb2.py"
    - "**/migrations/**"
    - "**/__pycache__/**"
    - "build/**"
    - "dist/**"
    - ".tox/**"
vendor:
  paths: [".venv/**", "venv/**", "**/site-packages/**", "vendor/**", "node_modules/**"]
  mode: collapsed
  parse: lazy
limits:
  file_lines: {warn: 400, error: 800}
  function_lines: {warn: 40, error: 100}
  functions_per_file: {warn: 20, error: 40}
  methods_per_class: {warn: 15, error: 30}
  function_params: {warn: 4, error: 7}
  cyclomatic_complexity: {warn: 10, error: 20}
  module_cycle: {warn: 0}
architecture:
  enabled: true
  profile: strict
cache:
  enabled: true
  path: .analyzer-cache
output:
  formats: [console]
```

Этот пример не привязан к фреймворку: он анализирует файлы выбранных языков, исключает тесты, миграции, сгенерированный код и артефакты сборки, задаёт пороги предупреждений `warn` и ошибок `error`. Порог `module_cycle` показывает циклы между модулями. Пути считаются от корня анализа, globs чувствительны к регистру. Правила `.gitignore` тоже учитываются; для анализа тестов удалите соответствующие исключения. Каталоги зависимостей отмечены отдельно и могут раскрываться при анализе связей.

Проверьте настройки и выполните анализ:

```sh
codefactor config check --file analyzer.yaml --strict
codefactor scan . --config analyzer.yaml --strict-config
codefactor config show --file analyzer.yaml --resolved
```

`scan .` автоматически находит `analyzer.yaml` или `analyzer.yml`. При анализе другого корня, например `scan ./src`, указывайте файл явно: `--config analyzer.yaml`. Параметры CLI имеют приоритет над YAML, YAML — над настройками по умолчанию.

### Готовые профили

| Профиль | Когда использовать |
| --- | --- |
| [minimal.yaml](examples/config/minimal.yaml) | Выбрать язык и начать с настроек по умолчанию |
| [medium.yaml](examples/config/medium.yaml) | Настроить исключения, основные пороги и кеш для ежедневной работы |
| [maximum.yaml](examples/config/maximum.yaml) | Настроить пороги для разных участков проекта, слои, наборы и расширенный анализ |
| [django.yaml](examples/config/django.yaml) | Проект на Django: исключения, слои `views → services → models` и внешние вызовы по раскладке `startapp` |
| [fastapi.yaml](examples/config/fastapi.yaml) | Сервис на FastAPI: исключения, слои `api → services → repositories → models` и клиенты по раскладке `app/` |

```sh
cp .venv/share/codefactor/examples/config/medium.yaml analyzer.yaml
```

Этот путь подходит для окружения `.venv` из примера установки. В другом окружении примеры находятся в `share/codefactor/examples` внутри каталога этого окружения.

Каждый пример самодостаточен. Профили `minimal`, `medium` и `maximum` не привязаны к фреймворку; в `maximum` пути слоёв, имена сущностей и каталоги сторонних библиотек служат примерами — замените их на свои. Профили `django` и `fastapi` описывают слои по стандартной раскладке этих фреймворков и подстраиваются под проект переименованием селекторов. Профиль `minimal` выбирает язык, сохраняя остальные настройки по умолчанию, включая архитектурный и алгоритмический анализ.

[Как выбрать и применить профиль](examples/README.md) · [Полный справочник YAML](docs/configuration.md). Доступные ключи установленной версии также показывает `codefactor config keys`.

## Изучение проекта в браузере

```sh
codefactor serve . --port 8080 --open --watch
```

Откройте `http://127.0.0.1:8080/`, если браузер не открылся автоматически. В интерфейсе доступны исходники с замечаниями, карта кода, графы вызовов, зависимости, архитектурные проверки и действующие критерии анализа. `--watch` обновляет анализ при изменении исходников; остановка — `Ctrl+C`. После редактирования YAML перезапустите сервер.

Сервер по умолчанию доступен только с этого компьютера. Если меняете `--host`, учитывайте, что подключённые пользователи получают доступ к исходникам анализируемого проекта.

## Полезные команды

```sh
codefactor metrics . --group-by directory
codefactor relations --a 'dir:src' --b 'dir:tests' --format md
codefactor external list --category db
codefactor --help
codefactor scan --help
```

`metrics` сравнивает показатели по группам; `relations` показывает вызовы между выбранными частями проекта; `external` перечисляет распознанные внешние операции. Замените `src` и `tests` на каталоги своего проекта. Для подробного графа вызовов используйте `codefactor graph --help` или откройте нужную функцию в веб-интерфейсе.

## Отчёты и CI

| Формат `scan` | Для чего использовать |
| --- | --- |
| `console` | Чтение результатов в терминале |
| `json` | Сохранение полного отчёта и дальнейшая обработка |
| `md` | Отчёт для ревью и документации |
| `sarif` | Передача замечаний в инструменты статического анализа |

```sh
python -m venv .venv
. .venv/bin/activate
python -m pip install --no-cache-dir -r requirements-codefactor.txt
codefactor config check --file analyzer.yaml --strict
codefactor scan . --strict-config --fail-on-warn --format sarif --out codefactor.sarif
```

Добавьте `requirements-codefactor.txt` и `analyzer.yaml` в репозиторий проекта. На Windows используйте активацию окружения из раздела установки.

Сохраняйте `codefactor.sarif` как артефакт CI. Для JSON замените формат на `json` и имя файла на `codefactor-report.json`. Логи идут в stderr отдельно от отчёта.

| Код завершения | Значение |
| --- | --- |
| `0` | Нет блокирующих замечаний |
| `1` | Предупреждения при `--fail-on-warn` либо ошибка выполнения команды |
| `2` | Найдены ошибки правил анализа |
| `3` | Синтаксическая ошибка YAML в основном файле конфигурации |

Без `--fail-on-warn` обычные предупреждения не блокируют проверку. Архитектурные замечания носят рекомендательный характер и не меняют код завершения, в том числе с `--fail-on-warn`: нарушения границ слоёв читайте из отчёта `sarif` или `json`. Чтобы цикл между модулями блокировал проверку, задайте порог `limits.module_cycle`: в профилях `medium`, `django` и `fastapi` он даёт предупреждение, в `maximum` — ошибку. При ошибке команды читайте stderr и диагностику отчёта.

### Подключение к существующему проекту

После просмотра первого отчёта сохраните принятые замечания в снимок допущений (baseline):

```sh
codefactor baseline create --root . --config analyzer.yaml --capture violations
codefactor scan . --strict-config --baseline-mode review --fail-on-warn
```

Снимок по умолчанию сохраняется в `.analyzer-baseline.yaml`. Принятое значение скрывается, пока не ухудшится: если для функции допущено 8 параметров, при 9 появится замечание «Допущено 8, сейчас 9» с уровнем действующего правила.

Чтобы сохранить все метрики и проверять ухудшения даже ниже обычных порогов, используйте полный снимок:

```sh
codefactor baseline create --root . --config analyzer.yaml --capture all --baseline accepted.yaml
codefactor scan . --baseline accepted.yaml --baseline-mode regressions --fail-on-warn
codefactor baseline update --root . --config analyzer.yaml --baseline accepted.yaml
```

Режим `review` применяет обычные пороги с учётом допущений; `regressions` дополнительно показывает ухудшения сохранённых показателей. Оба режима доступны также у `metrics`. Сканирование не меняет снимок: новое состояние принимается только через `baseline update`. Проверка без допущений — `scan . --no-baseline`.

Старые `.analyzer-baseline.json` продолжают читаться; перед режимом `regressions` обновите их через `baseline update --baseline .analyzer-baseline.json`. Проверьте снимок и закоммитьте вместе с `analyzer.yaml`. В `.gitignore` добавьте `.analyzer-cache/` и создаваемые отчёты. Формат файла, выбор путей и правила сравнения описаны в [справочнике снимков допущений](docs/configuration.md#снимки-допущений-и-проверка-ухудшений).

## Обновление

Версия пакета и версия Core независимы. В основном `analyzer.yaml` можно выбрать последний стабильный Core или закрепить точную версию:

```yaml
core:
  version: latest  # либо "0.1.3"
```

Чтобы скачать выбранный Core без обновления библиотеки и lock-файла:

```sh
python -m codefactor core update
python -m codefactor --version
```

Для другого YAML используйте `python -m codefactor core update --config path/to/analyzer.yaml`. Команда соблюдает закрепление; для смены версии измените конфиг. Переменная `CODEFACTOR_CORE_VERSION=0.1.3` переопределяет YAML, в том числе при исходной сборке Python/Cargo. Версия должна быть строкой `latest` или `X.Y.Z`; диапазоны и префикс `v` не поддерживаются. `core.version` читается только из основного файла, не из `include`.

Бинарники сохраняются в `.codefactor/core/` рядом с выбранным YAML, без конфига — в текущем проекте. Добавьте этот каталог в `.gitignore`. Все четыре интеграции используют один формат кеша; разные проекты обновляются независимо. При обычном запуске CLI/API сетевых проверок нет. Если закреплённой версии ещё нет, выполните `core update`; команда также восстанавливает повреждённый кеш. При неудачном скачивании рабочая версия сохраняется.

`CODEFACTOR_BINARY` и явный путь в API по-прежнему выбирают локальный исполняемый файл. При `CODEFACTOR_BINARY` команда обновления только сообщает о внешнем бинарнике, без скачивания и замены файла. Чтобы запустить старый Core со строгой проверкой YAML, задайте версию через `CODEFACTOR_CORE_VERSION`, не добавляя неизвестную ему секцию `core`.

Готовый Python wheel и Cargo executable содержат исходный Core. После установки выполните `core update` из проекта, чтобы применить его YAML и получить другой бинарник. Пересборка или переустановка пакета для этого не нужна.

## Если что-то не работает

- **Команда не найдена:** активируйте `.venv` или используйте полный путь к команде из раздела установки.
- **Осталась старая версия анализатора:** выполните `python -m codefactor core update`.
- **Ошибка установки из GitHub:** проверьте, что Git доступен в `PATH`, а репозиторий пакета опубликован.
- **Ошибка HTTPS:** проверьте доступ к GitHub и доверенные сертификаты.
- **Настройки не применяются:** запускайте из корня проекта или передайте `--config analyzer.yaml`; используйте `config check --strict` и `config show --resolved`.
- **Нужна установка через корпоративное зеркало:** `CODEFACTOR_RELEASE_BASE_URL` задаёт HTTPS-адрес зеркала, `CODEFACTOR_CA_BUNDLE` — доверенный сертификат. `CODEFACTOR_BINARY` позволяет использовать уже скачанный бинарь нужной платформы вместо сетевой загрузки.

## Как читать результаты

Статический анализ может не определить часть динамических вызовов, рефлексии и метапрограммирования. Оценки алгоритмической сложности описывают рост числа операций, а не измеренное время выполнения. Проверяйте диагностику разбора и определения связей; отсутствие замечания не доказывает отсутствие проблемы. Дополнительные архитектурные гипотезы профиля `extended` требуют проверки человеком.
